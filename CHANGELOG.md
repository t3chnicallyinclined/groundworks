- **Secret refusal: path-shaped runs are not key material** (2026-10-30, Rust workspace; gw-security ruling 4, applied as written, plus one extension). Inside the high-entropy rule only (the named patterns and kv-secret still run first, unchanged), a candidate run is skipped when `refusal::path_shaped` holds. A question no unit matches is `NO_HITS`, written and rendered as 0 hits rather than raised or filled with the first rows (`BM25.rank` returns nothing for it; the bake-off tests already pinned that). Docs are opt-in per invocation by design: `xscholar/panel/PROTOCOL.md` carries worked examples from another instance and would fail check (c).
- **Bitemporal claims** (V2-2, `xscholar/temporal.py`): `valid_from`/`valid_to` on facts for when a claim held in the source; `learned_at` and an append-only `status_history` on facts (`ready_history` on conclusions) written by a datastore event only when the value changes, so loader re-writes append nothing and history can neither be emptied nor rewritten; `as_of(db, table, id, when)` and `snapshot(db, when)` answer "what did the graph say on date X"; `Writer.propose`/`confirm` take optional valid dates; `run_instance.py` applies it after the gates and reports a `temporal` count in health. Tested both ways on a throwaway SurrealDB 3.1.6, including the proof that removing the no-op guard makes a same-status re-write append (and that an event with no guard at all recurses until the write is rejected).
- **Lens builder from config** (V2-1, `xscholar/lens.py`): the `lenses:` section is now a defined shape (kind, charter, standard, filter, backing; frame and crosswalk for a framework lens) that `config.py` validates, refusing a standard looser than the base gates, a filter over anything but label fields, and a crosswalk outside the vocabulary. Each perspective or discipline lens becomes a datastore view `lens_<name>` (`DEFINE TABLE ... AS SELECT ... FROM label` with the standard on `unit.status`/`unit.grade`); a framework lens becomes `consideration` nodes and `falls_under` filings with stable edge ids and a sweep only after success, plus a per-node matrix by direction, usable vs unusable. New MCP read tool `lens_view(name, limit)` (15 tools now); `health` lists the lenses with kind and backing; `xscholar lens INSTANCE.yaml --emit | --apply`; `run_instance.py` applies the views and prints the matrix. Tested both ways on the demo instance (`tests/test_lens.py`): an out_of_window tier-3 probe never reaches `service_owner`, and the same view with its standard removed is shown to leak it. Measured caveat on 3.1.6: a view refreshes only from `label`, so a later unit change is reported as `drift` until the views are rebuilt.
- **Change-feed work queue** (V2-4, `xscholar/queue.py`): `CHANGEFEED ... INCLUDE ORIGINAL` on the unit, claim, critique and cites tables via `ALTER TABLE` (the bare `DEFINE TABLE OVERWRITE ... CHANGEFEED` form silently drops SCHEMAFULL on 3.1.6); a worker that reads `SHOW CHANGES ... SINCE <versionstamp>` per table, dispatches before/after images to handlers, and stores the versionstamp only after every handler returns (at-least-once; handlers idempotent by deterministic ids); first consumers `stale_recheck` and `archive_on_delete`. Tested both ways on a throwaway server: resume after a stop with nothing missed and nothing twice, a raising handler re-delivered, and a deliberate break (advance first) shown to lose the change. Known limits: 3.1.x deletes carry no before-image, so the worker caches the last image it saw of claim rows; a worker down longer than the retention window loses the gap.

- **Compose packaging** (V2-6, tier 1) -- **superseded in this same release: removed by the "Docker removed" entry above; nothing below ships at v0.2.0**: `Dockerfile` (python:3.13-slim, core install only, no torch); `compose.yaml` with `surrealdb` (`surrealdb/surrealdb:v3.1.6`, rocksdb storage on a named volume, an `is-ready` healthcheck, 127.0.0.1-only ports), `engine` (builds from the Dockerfile, waits for surrealdb healthy, runs `scripts/run_instance.py` against it), `backup` (profile `ops`, scheduled `surreal export` into `./backups`), and an `embed` placeholder (profile `gpu`, no CUDA image pulled); `.env.example`, `.dockerignore`, and `scripts/compose_check.sh` (config validation plus, where Docker is reachable, a real run checked for `0 misbehaved` and `"DRIFT_confirmed_without_valid_cite": [{"n": 0}]`). README documents `docker compose up --build engine` and notes SurrealDB's BSL 1.1 license ships with the image and must stay conspicuous (`docs/LICENSING.md` s.1). Kubernetes deliberately not included (tier 1 is one box).
- **Per-agent credentials** (V2-3, `xscholar/access.py`): an optional `access:` section (roles with `read`, `write`, `lens_bound`) that `config.py` validates; from it one `DEFINE ACCESS agent ON DATABASE TYPE RECORD` over an `agent` table plus an `ALTER TABLE ... PERMISSIONS` clause on every generated table, so the datastore, not the server, decides who writes what: a role SELECTs only its `read` tables, CREATEs/UPDATEs/RELATEs only its `write` tables, a lens-bound seat writes critiques only where `lens = $auth.lens`, only `loader` writes labels, DELETE is NONE for every role (root and the archive only), and the gates stay in force for every credential. `provision`/`revoke`/`connect` and `xscholar.access --emit | --apply | --provision AGENT ROLE [--lens L] | --revoke AGENT` print the launch env (`XSCHOLAR_DB_USER/PASS/ACCESS`); `Db` signs in through the record access and, because SurrealDB answers a denied write with an empty result and status OK, raises `PermissionDenied` (reported by MCP as `rejected_by_gate`) instead of reporting success; `run_instance.py` runs the demo scenario as three provisioned identities and prints who did each step. Tested both ways on a throwaway SurrealDB 3.1.6 (`tests/test_access.py`), one probe pair per rule, including the proof that a loosened critique clause lets a reader's critique through and that root's gate probes still pass after access is applied. Measured: `DEFINE USER ... ON DATABASE` is a system user and bypasses PERMISSIONS, so it cannot carry these rules.

## 0.1.0b1 (unreleased, 2026-09-15)

First beta: the engine runs a complete instance from one config file, agents work through MCP, and every layer has a fixed test.

### The system
- **Instance config as the single source of truth** (`xscholar/config.py`): the eight answers in one YAML or JSON file, validated with every error listed. A strict YAML subset parser with no third-party dependency.
- **Generated schema, gates and probes** (`xscholar/gates.py`): one datastore ASSERT per rule, and for every rule a write that must be refused plus the same write accepted once the evidence exists. Proven to catch a weakened gate and to refuse raw writes, not only helper calls.
- **Pipeline** (`xscholar/pipeline/`): intake with contract checks and exclusion logging; chunker (every unit in exactly one slice); validator (coverage, vocabulary, tier rules, verbatim quotes); loader with stable edge ids and a sweep that a failed write blocks; the typed write surface that stamps provenance and explains every refusal; the label-agreement harness (kappa, per-field agreement, adjudication list).
- **Panel protocol** (`xscholar/panel/`): blind round, anonymized cross-examination, verbatim flaw quotes, locked panel, stance lines, dissent quota, novelty and agreement checks, owner-held thresholds and confidence weights, weighted tally with splits returned to the human.
- **Reading layer** (`xscholar/present/`): renderings for human verification with 100% preservation, check-first ordering, the inline rule re-check, seeded-error planting and reviewer scoring.
- **MCP front door** (`xscholar/mcp/`): 14 domain-free tools; a generic adapter gives any instance the full set with no adapter code; gate refusals come back as `rejected_by_gate` with what is missing named; source text only under an untrusted key.
- **Hooks** (`xscholar/hooks/`): a session-start line that warns when the graph is off, and a pre-tool lookup that explains unit and claim ids and flags an eliminated claim about to be repeated.
- **Retrieval bake-off** (`xscholar/embed/`): local embeddings against a keyword baseline with confidence intervals.
- **Demo instance** (`instances/demo-incident`): a complete non-legal instance, runnable in one command, labelled by real agents in the first run.

### Measured on the way (generic numbers; details in `notes/`)
- Keyword search beat two embedding models and a hybrid on a 7,995-unit corpus; no model adopted.
- Six real panels: 3 consensus, 3 splits; 0 of 18 stances changed between rounds; anonymization showed no effect at n=1.
- Reading-layer reviewers: relabelled claims were caught 0 of 9 times by reading alone in three layouts; a tuned rule re-check flags them with 0 false flags on clean documents; a flag that says only "fails a rule" was still skipped (wording is the next variable).
- Two agents labelled the demo instance: 66 of 66 validated on the first run; agreement with the intended reading, tier kappa 0.93.

### Known gaps (why this is a beta)
- The first private instance still runs on its own schema; moving it onto the engine is scheduled by its owner.
- Role skills and lens views are not yet generated from the config.
