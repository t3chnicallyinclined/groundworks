# Changelog

## 0.2.0 (unreleased)

- **Engine renamed XScholar -> Groundworks** (decided 2026-09-17, before the first tag): package
  `xscholar/` -> `groundworks/`, console script `xscholar` -> `groundworks`, every `XSCHOLAR_*`
  environment variable -> `GROUNDWORKS_*` (hard cutover, old names no longer read), the MCP
  server's advertised name and instructions string, scratch/table name prefixes, and docs,
  `.claude/` agent and skill files. Hindsight (the cross-project lessons layer) keeps its own
  name. Past releases below stayed named XScholar; only the current and future name changed.

- **An instance declares its own node tables and edge types** (V2-17, and V2-8/V2-9 through it; `xscholar/config.py`, `gates.py`, `access.py`, `skills.py`, `pipeline/write.py`, `instances/demo-incident/instance.yaml`): the graph shape was two constants in engine code -- `gates.EDGES` and `access.NODE_TABLES` -- so a domain needing `event`, `person`, `citation` rows or a `mentions`/`preserves` edge could not have one without editing the engine, and eleven such gaps were queued behind it (`notes/2026-09-15_engine_gaps_from_instance_config.md`). `instance.yaml` now takes optional `tables:` and `edges:` sections (`edges` carry `from`, `to` and typed, optionally enumerated fields); the engine keeps `config.BUILT_IN_NODE_TABLES` / `config.BUILT_IN_EDGES` and every reader asks the instance instead: schema generation, gate traversals, accept/wrong-evidence/forbidden-evidence probes, probe cleanup, `access:` PERMISSIONS (including lens binding, which now follows a declared `lens` field rather than a fixed list), the generated role skills, and a new `Writer.relate(edge, source, target, **fields)`. A declared name colliding with a built-in table or edge, a name declared twice, an edge end that is not a node table, and an unknown field type are each refused at load time with the name in the message; both sections are optional, so every existing config is unchanged. Three things the declared path forced, each of which was already a hole for the built-ins: the accept probe builds its evidence from the clause (it was a ladder of table names with no `else`, so a clause whose source table it did not recognise silently produced **no** fix statements at all and the run still had to call that behaviour); the wrong-evidence probe is generated for any constrained clause whose field has a domain the engine knows (it was hard-coded to the edge being named `cites`) and is otherwise reported untested with the reason; and a write the probe itself cannot make is now reported as `setup_error` instead of ending the whole run with a traceback. `judge()` gained `missing_accept_probe` (a requires clause with no evidence, or evidence the datastore says does not match the clause) and the `setup_error` guard; `spec()`/`compare_baseline()` now pin what each edge a rule uses joins, so repointing a declared edge is a weakening rather than an invisible change of meaning; a gate on a declared field no longer overwrites that field's declared type and enumeration. **Demo instance** (baseline regenerated): `edges.preserves{how}` (unit -> conclusion) with a `requires preserves min 1` clause on readiness -- V2-8, exception recorded as `how: not_captured` and visible on the edge -- and `edges.verified_from` (authority -> unit) with `authority.verified` gated on `grade = 'official_text'` -- V2-9, where the refused citation in the test is usable and confirming-grade and is refused solely for not being the official text. Neither needed an engine change. 19 new tests, each run red against a named mutation first. **Known limits, not worked around:** a clause's `where` constrains the far node, never the edge's own fields; and a rule's clauses are ANDed, so "this OR a recorded exception" is not expressible -- which is why V2-8's exception is an edge carrying a reason rather than a marker on the conclusion.
- **Docker removed; the database version is checked instead** (`Dockerfile`, `Dockerfile.backup`, `compose.yaml`, `.dockerignore`, `.env.example`, `scripts/compose_check.sh`, `scripts/backup_loop.sh` deleted; `xscholar/db.py`): 213 lines of packaging that nothing imported, no test exercised, CI never referenced, and that had never been run once -- while the README described it as a way to run the system. The engine's `dependencies` are `[]`, so the real requirement is Python plus the SurrealDB binary. Pinning the database version was the only thing the image genuinely bought, and a version is a fact the server will tell you: `Db.version()` reads `/version` and `Db.version_problem()` refuses a different major series by name -- this engine's behaviour is *measured* against 3.1 (a schema re-apply silently drops a CHANGEFEED, a delete carries no before-image, `DEFINE USER ... ON DATABASE` bypasses table PERMISSIONS, a denied write returns an empty result with status OK), and each of those is load-bearing somewhere here. A different 3.x minor prints a warning rather than refusing; `ping(check_version=False)` opts out. Verified against a real server (accepted 3.1.6, refused when the measured series was changed) and by six tests that need no server. The README now documents a persistent database and `surreal export` on the host's own scheduler, which is one line that fails visibly.
- **`forbids` clauses are probed, in both directions** (`xscholar/gates.py`, `instances/demo-incident/gate_baseline.json`): a gate expression has two halves and only one was ever tested. `fix` satisfied `requires`; `wrong` fired only for `cites`; nothing ever created the row a `forbids` clause excludes and checked that the datastore refused the write. Both `forbids` clauses could be deleted from the demo config and the probe report still said `misbehaved: 0` -- only the baseline caught it. `probes()` now generates a forbidden-evidence probe per clause, built entirely from the clause (`edge` gives the table and the direction of the RELATE, `where` -- expanded exactly as the gate expression is -- gives the field values, `min` gives the count): it writes the row, asks the datastore with the clause's own predicate whether what it wrote really matches, requires the promotion to be REFUSED, removes the row, confirms the traversal is empty again and requires the same promotion to be ACCEPTED. A clause it cannot turn into a row (anything but a conjunction of `field = literal` / `field IN [literals]`) is reported as untested and fails `behaved`, mirroring `constrained`/`missing_probe` -- silently generating nothing was the original defect. `judge()` fails a rule that forbids something and produced no forbidden-evidence result; `compare_baseline()` also compares the new `forbidden_evidence_reject` flag; the report gains `forbidden_refused_ok` and `forbids_untested` counts and the run prints a FORBIDS line. Cleanup now names `label` and every edge table, and the probe-rows-left-behind test counts all of them. Measured: with the forbids clauses deleted from the config and applied to a throwaway server, the strict instance's probes go from `misbehaved: 0` to `misbehaved: 1` with `reject: false` on both clauses; every new test was run red against a named mutation first.
- **Gate baselines, and probes that notice they stopped testing** (defect found by a second session using the engine; `xscholar/gates.py`, `instances/demo-incident/gate_baseline.json`): `misbehaved: 0` meant "every gate matches its own current spec", not "the spec is still strong". Deleting a `where` clause from a promotion rule stopped the sharper wrong-evidence probe being generated, so the report stayed green -- `rejected_ok: 2`, `accepted_ok: 2`, `misbehaved: 0`, the only trace being `wrong_evidence_reject` flipping from `true` to `null` -- while the datastore began accepting a fact confirmed on a document-only citation. Two checks close it. (1) `probes()` now records `constrained`/`constraints` per rule, and `judge()` (extracted from `run_probes` so the test exercises the shipped decision, not a copy of it) treats `wrong_evidence_reject: null` on a constrained rule as a **failure** naming the constraint, instead of "not applicable". (2) `spec(inst)` states what the rules claim with no database involved, and `compare_baseline()` fails a run for a rule that disappeared, a `requires`/`forbids` clause that was dropped, a lowered `min`, or a probe flag that was `true` and is no longer; adding a rule or a clause is not a failure. `xscholar.gates --write-baseline PATH` writes the file (human-owned: commit it, review every diff) and `--baseline PATH` compares, exiting 1 on weakening and 2 if the baseline is missing. The spec half needs no server, so `tests/test_gate_baseline.py` runs it over every `instances/*/gate_baseline.json` in the ordinary suite; CI also runs the flag half against a throwaway server. Tested both ways on a live server (`tests/test_gates.py`): the end-to-end test reproduces the blind spot honestly -- the weakened config's own probes still report `misbehaved: 0` -- then shows the strict probes catching the datastore accepting wrong evidence, and the baseline catching the same edit from the config alone. Deliberately weakened and shown to go red, naming each lost clause.
- **Role skills and a drift guard generated from config** (V2-5, C1 remainder, C8; `xscholar/skills.py`, `xscholar/drift.py`, `xscholar/skills_templates/`): one `SKILL.md` per `roles:` entry, rendered from a per-skill template (`red-team`, `cold-bench`, `premortem`, `claim-audit`, `reader`) filled entirely from the instance -- goal and holder, the whole vocabulary with the confirming grades and usable statuses spelled out, each seat's lens charter with its `backing` and `signed` (a prompt-backed or unsigned charter says in the skill that it may never support promotion), the role's panel options, objection categories and weighted seat, the exact `panel.py lock/anonymize/check/tally` sequence with `--settings`, every readiness gate rewritten from `gates:` into plain words with `$confirming`/`$usable` expanded, the MCP tools the role may call filtered by its `access:` grant (with the refused ones named), and the `privacy:` rules. A role whose `skill:` has no template is an error naming the role, never a silent skip. Each file carries `GENERATED from <instance id> by xscholar.skills; edit the config, not this file` and a `content-sha256` over its own body; generating twice is byte-identical. `xscholar/drift.py` checks three things and names file plus item for each: every lens, seat, panel option, objection category and gate id in the config appears in the skill that uses it (whole-token match, so `owner` is not satisfied by `service_owner`); every file still hashes to a fresh generation, separating a hand edit (its own hash line no longer matches) from a stale file (the config moved); and, for any docs passed, every `lens_<name>`/`seat_<name>` mentioned exists in the config. Missing and orphan skill files are drift too. `xscholar skills generate`, `xscholar drift`, a CI step, and the last step of `xscholar test`. The demo instance's skills are generated into `instances/demo-incident/skills/`. Tested both ways (`tests/test_skills_drift.py`, 36 tests, no server): renaming a seat, renaming a panel option, editing a generated file, a stale file whose own hash is self-consistent, a missing file, an orphan file, a doc naming an unknown lens, and an untemplated role each fail with the item named, and restoring passes. Both guards were deliberately weakened and shown to go red. Docs are opt-in per invocation by design: `xscholar/panel/PROTOCOL.md` carries worked examples from another instance and would fail check (c).
- **Bitemporal claims** (V2-2, `xscholar/temporal.py`): `valid_from`/`valid_to` on facts for when a claim held in the source; `learned_at` and an append-only `status_history` on facts (`ready_history` on conclusions) written by a datastore event only when the value changes, so loader re-writes append nothing and history can neither be emptied nor rewritten; `as_of(db, table, id, when)` and `snapshot(db, when)` answer "what did the graph say on date X"; `Writer.propose`/`confirm` take optional valid dates; `run_instance.py` applies it after the gates and reports a `temporal` count in health. Tested both ways on a throwaway SurrealDB 3.1.6, including the proof that removing the no-op guard makes a same-status re-write append (and that an event with no guard at all recurses until the write is rejected).
- **Lens builder from config** (V2-1, `xscholar/lens.py`): the `lenses:` section is now a defined shape (kind, charter, standard, filter, backing; frame and crosswalk for a framework lens) that `config.py` validates, refusing a standard looser than the base gates, a filter over anything but label fields, and a crosswalk outside the vocabulary. Each perspective or discipline lens becomes a datastore view `lens_<name>` (`DEFINE TABLE ... AS SELECT ... FROM label` with the standard on `unit.status`/`unit.grade`); a framework lens becomes `consideration` nodes and `falls_under` filings with stable edge ids and a sweep only after success, plus a per-node matrix by direction, usable vs unusable. New MCP read tool `lens_view(name, limit)` (15 tools now); `health` lists the lenses with kind and backing; `xscholar lens INSTANCE.yaml --emit | --apply`; `run_instance.py` applies the views and prints the matrix. Tested both ways on the demo instance (`tests/test_lens.py`): an out_of_window tier-3 probe never reaches `service_owner`, and the same view with its standard removed is shown to leak it. Measured caveat on 3.1.6: a view refreshes only from `label`, so a later unit change is reported as `drift` until the views are rebuilt.
- **Change-feed work queue** (V2-4, `xscholar/queue.py`): `CHANGEFEED ... INCLUDE ORIGINAL` on the unit, claim, critique and cites tables via `ALTER TABLE` (the bare `DEFINE TABLE OVERWRITE ... CHANGEFEED` form silently drops SCHEMAFULL on 3.1.6); a worker that reads `SHOW CHANGES ... SINCE <versionstamp>` per table, dispatches before/after images to handlers, and stores the versionstamp only after every handler returns (at-least-once; handlers idempotent by deterministic ids); first consumers `stale_recheck` and `archive_on_delete`. Tested both ways on a throwaway server: resume after a stop with nothing missed and nothing twice, a raising handler re-delivered, and a deliberate break (advance first) shown to lose the change. Known limits: 3.1.x deletes carry no before-image, so the worker caches the last image it saw of claim rows; a worker down longer than the retention window loses the gap.

- **Compose packaging** (V2-6, tier 1): `Dockerfile` (python:3.13-slim, core install only, no torch); `compose.yaml` with `surrealdb` (`surrealdb/surrealdb:v3.1.6`, rocksdb storage on a named volume, an `is-ready` healthcheck, 127.0.0.1-only ports), `engine` (builds from the Dockerfile, waits for surrealdb healthy, runs `scripts/run_instance.py` against it), `backup` (profile `ops`, scheduled `surreal export` into `./backups`), and an `embed` placeholder (profile `gpu`, no CUDA image pulled); `.env.example`, `.dockerignore`, and `scripts/compose_check.sh` (config validation plus, where Docker is reachable, a real run checked for `0 misbehaved` and `"DRIFT_confirmed_without_valid_cite": [{"n": 0}]`). README documents `docker compose up --build engine` and notes SurrealDB's BSL 1.1 license ships with the image and must stay conspicuous (`docs/LICENSING.md` s.1). Kubernetes deliberately not included (tier 1 is one box).
- **Per-agent credentials** (V2-3, `xscholar/access.py`): an optional `access:` section (roles with `read`, `write`, `lens_bound`) that `config.py` validates; from it one `DEFINE ACCESS agent ON DATABASE TYPE RECORD` over an `agent` table plus an `ALTER TABLE ... PERMISSIONS` clause on every generated table, so the datastore, not the server, decides who writes what: a role SELECTs only its `read` tables, CREATEs/UPDATEs/RELATEs only its `write` tables, a lens-bound seat writes critiques only where `lens = $auth.lens`, only `loader` writes labels, DELETE is NONE for every role (root and the archive only), and the gates stay in force for every credential. `provision`/`revoke`/`connect` and `xscholar.access --emit | --apply | --provision AGENT ROLE [--lens L] | --revoke AGENT` print the launch env (`XSCHOLAR_DB_USER/PASS/ACCESS`); `Db` signs in through the record access and, because SurrealDB answers a denied write with an empty result and status OK, raises `PermissionDenied` (reported by MCP as `rejected_by_gate`) instead of reporting success; `run_instance.py` runs the demo scenario as three provisioned identities and prints who did each step. Tested both ways on a throwaway SurrealDB 3.1.6 (`tests/test_access.py`), one probe pair per rule, including the proof that a loosened critique clause lets a reader's critique through and that root's gate probes still pass after access is applied. Measured: `DEFINE USER ... ON DATABASE` is a system user and bypasses PERMISSIONS, so it cannot carry these rules.

## 0.1.0b1 (unreleased, 2026-09-15)

First beta: the engine runs a complete instance from one config file, agents work through MCP, and every layer has a fixed test.

### The system
- **Instance config as the single source of truth** (`xscholar/config.py`): the eight answers in one YAML or JSON file, validated with every error listed. A strict YAML subset parser with no third-party dependency.
- **Generated schema, gates and probes** (`xscholar/gates.py`): one datastore ASSERT per rule, and for every rule a write that must be refused plus the same write accepted once the evidence exists. Proven to catch a weakened gate and to refuse raw writes, not only helper calls.
- **Pipeline** (`xscholar/pipeline/`): intake with contract checks and exclusion logging; chunker (every unit in exactly one slice); validator (coverage, vocabulary, tier rules, verbatim quotes); loader with stable edge ids and a sweep that a failed write blocks; the typed write surface that stamps provenance and explains every refusal; the label-agreement harness (kappa, per-field agreement, adjudication list).
- **Panel protocol** (`xscholar/panel/`): blind round, anonymized cross-examination, verbatim flaw quotes, locked panel, stance lines, dissent quota, novelty and agreement checks, owner-held thresholds and confidence weights, weighted tally with splits returned to the human.
- **Reading layer** (`xscholar/present/`): renderings for human verification with 100% preservation, check-first ordering, the inline rule re-check, seeded-error planting and reviewer scoring.
- **MCP front door** (`xscholar/mcp/`): 14 domain-free tools; a generic adapter gives any instance the full set with no adapter code; gate refusals come back as `rejected_by_gate` with what is missing named; source text only under an untrusted key.
- **Hooks** (`xscholar/hooks/`): a session-start line that warns when the graph is off, and a pre-tool lookup that explains unit and claim ids and flags an eliminated claim about to be repeated.
- **Retrieval bake-off** (`xscholar/embed/`): local embeddings against a keyword baseline with confidence intervals.
- **Demo instance** (`instances/demo-incident`): a complete non-legal instance, runnable in one command, labelled by real agents in the first run.

### Measured on the way (generic numbers; details in `notes/`)
- Keyword search beat two embedding models and a hybrid on a 7,995-unit corpus; no model adopted.
- Six real panels: 3 consensus, 3 splits; 0 of 18 stances changed between rounds; anonymization showed no effect at n=1.
- Reading-layer reviewers: relabelled claims were caught 0 of 9 times by reading alone in three layouts; a tuned rule re-check flags them with 0 false flags on clean documents; a flag that says only "fails a rule" was still skipped (wording is the next variable).
- Two agents labelled the demo instance: 66 of 66 validated on the first run; agreement with the intended reading, tier kappa 0.93.

### Licensing
- Proprietary (`LICENSE`); adapted material and dependencies in `THIRD_PARTY_NOTICES.md`; a license check and a privacy scan run at every commit.

### Known gaps (why this is a beta)
- The first private instance still runs on its own schema; moving it onto the engine is scheduled by its owner.
- Role skills and lens views are not yet generated from the config.
- Per-agent datastore credentials, change-feed work queue, and bitemporal columns are designed, not built.
- Label accuracy has been measured only against a rule stub; two independent agents with human adjudication on a real instance is still owed.
