# Does Groundworks help an agent answer questions about its owner's projects? (eval, October 2026)

A report on two evaluation sets, twelve pre-registered runs, and what changed because of them. Every number
here comes from a run folder with its pre-registration, results and report; the folders live in the owner's
private Groundworks home, not in this repository. Dollar figures are Claude Code's API-equivalent estimates;
the runs ran on a subscription.

## The question and the method

Groundworks ingests a set of repositories into a store (text units with file, lines, hash, date and expert
tags) and gives an agent tools to ask questions against them: `ask` (a ranked packet of candidates, in full,
numbered) and `answer` (a check that every quote in the answer is really in a candidate the agent read).
The claim to test: an agent with these tools answers the owner's hard questions at least as well as the same
agent with grep over the same files, for no more tokens, and never re-derives a lesson already recorded.

Method, fixed before each run (`prereg*.json` in each set's folder):

- Fresh headless Claude Code session per question, in an empty folder (no project memory, no CLAUDE.md),
  plugin off, only read tools. Arms differ in one thing each.
- A separate session with no tools grades each answer against an owner-approved gold answer, blind to the
  arm: correct / partial / wrong / abstained, plus "confidently wrong".
- Rates carry 95% Wilson intervals; two rates differ only when the intervals do not overlap. Token counts are
  compared pairwise per question. The noise floor was measured: the same configuration varies by about ±4
  correct on 47 questions and ±2 on 20.
- The question sets are checked by a program before any run: every gold quote must be word for word at its
  line in a tracked file, and every trap's false premise must be absent from its project.

## Set 1 (ask-v1): 47 questions answerable from the repositories

Lessons learned, things re-derived more than once, retracted claims, two documents that disagree, and five
traps with false premises. All answers exist in plain text in tracked files.

| Run | Arm | Correct | Confidently wrong | Median tokens |
|---|---|---|---|---|
| r1 | plain grep (Opus) | 39/47 | 0 | 138k |
| r1 | Groundworks, first agent text | 36/47 | 2 | 184k |
| r2 | Groundworks, question mode | 38/47 | 2 | 131k |
| r3 | + retry on the same packet, related projects | 36/47 | 2 | 93k |
| r4h | plain grep (Opus, high effort) | 35/47 | 0 | 120k |
| r4h | Groundworks (Opus, high effort) | 39/47 | 1 | 117k |
| r3f | plain grep (Fable 5.1) | 37/47 | 1 | 94k |
| r3f | Groundworks (Fable 5.1) | 36/47 | 0 | 98k |

Result: no evidence either way. Grep is good at finding plain text in documents; a set where every answer is
written down cannot show the difference. What the set did show was where the tokens went (a start-of-work
routine run on every question, blocked writes, quotes refused and re-asked) and that finding was never the
problem: a Groundworks tool put the gold file in front of the agent on its first call on 42 of 42 non-trap
questions. The misses were reading two sources that disagree.

A cheap router ("are these candidates enough to answer?") was also tested and ruled out: a small model's
judgement was right 67% of the time it said yes at its highest confidence; a BM25 score threshold 59%.

## Set 2 (ask-v2): 47 reworded + 20 questions whose only source is the owner's notes

The 47 were reworded (same gold, new wording and angle). The 20 are lessons that exist only in the owner's
agent-memory notes, which were ingested as a private project linked (`related`) from every project. The
owner-approved gold answers of set 1 were recorded as facts before the run; recording stayed off during runs.

Agent against cold grep: the intervals do not overlap (the first pre-registered separation). Against grep with

was among what the agent read on 45 of 47 reworded questions.

## What was wrong, and what was fixed

Each item was found by a run and checked by the next one.

1. **The agent misused the tools.** The output style written for doing work made it open every question with
   a start-of-work routine, write to the journal (blocked), and never call `ask`. Fix: a question mode in the
   agent text, shipped as a plugin agent and as the output style (one text, a test keeps them equal).
2. **Search was word-based only.** Identifiers, numbers and error strings were matched loosely. Fix: `grep`,
   an exact or regex match over the ingested units, scoped and dated.
3. **Typed quotes failed the exact check 14-40% of the time.** Models find the passage, not the span. Fixes,
   in order of what the runs showed: quotes as line ranges copied by the program; near-miss quotes aligned to
   their span (>= 80% of words in order); a recorded fact quotable by its own text; short quotes accepted word
   for word; empty quote objects ignored; a range running past its candidate cut to it; a packet that failed
   its check answerable again without a new `ask`.
4. **Reach.** A question filed under the notes project could not see the repository the answer lived in; a
   project may now list `related` projects, read with it.
5. **Crowding.** A packet of 20 built from a 7,000-unit repository never showed a note from an 800-unit
   project, even when that note ranked first inside its own project. Every project read now keeps three places.
6. **Dates.** Units carry when their file last changed; a note's own frontmatter date beats the commit date
   (a folder committed in one snapshot otherwise dates every note the same day).
7. **Facts first.** Recorded facts rank above the files in a packet, and an answer that passes can be recorded
   as a fact with its quote re-checked, so the next session gets the checked answer first.
8. **Measurement.** The runner logs every tool call, when the gold was first seen, whether a recorded fact was
   read, and the text of every refusal; the report counts refusals by rule. A retrieval-only measure runs with
   no model (gold ingested, rank of the gold unit).

Three mistakes made along the way are recorded in the commit log: a build folder pushed to the public repository
and removed; a commit that did not compile pushed because a command chain ran the old binary past the failed
build; a commit whose message was a shell script. Each is fixed in the commit after it and named there.

## What this does and does not show

- On questions whose answers are written plainly in the repositories, Groundworks ties grep. The value is not
  there.
- On lessons that live only in notes, Groundworks separates from cold grep on correctness, and from the owner's
  everyday setup (grep plus a memory index) on tokens, at equal or better correctness.
- Recording works mechanically: checked answers come back first next time. Whether knowledge accumulates in
  real use is not yet measured: every run here used facts seeded from approved gold, with recording off.
- 47 and 20 questions bound what can be seen. Effects smaller than about 4 and 2 correct answers are noise, and
  the tables above should be read with that in mind.

## Retrieval ladder, r1 (2026-10-26, no model)

A packet is 20 candidates read in full, measured at 14k tokens on average and 25k at most. The store ranks
each project with its own full-text index, so a read that spans projects is sorted by scores from different
indexes. The ladder (`groundworks eval-retrieval --ladder`, pre-registered before the run) takes the read at
depth 60 with recorded facts excluded, reorders it on this side of the store, and asks where the gold unit
lands. Arms: the store's order; BM25 over the pool (its own document frequencies), plain and with the store's
own stemming, and with the locator's path words as a second field; reciprocal rank fusion of the store's order
and stemmed BM25. No constant was tuned. Set 2 decides, set 1 replicates; a gold unit outside the pool (14 of
104) counts as rank 61 for every arm.

| arm | set 2: gold at rank 1 (95% CI) | top 20 | paired vs store (wins/losses, sign test) | set 1: gold at rank 1 |
|---|---|---|---|---|
| store | 16/62 (26%, 17-38) | 44 | - | 5/42 |
| bm25 | 28/62 (45%, 33-57) | 52 | 29/8, p = 0.001 | 10/42 |
| bm25-stem | 25/62 (40%, 29-53) | 52 | 29/9, p = 0.002 | 9/42 |
| bm25-fields | 28/62 (45%, 33-57) | 51 | 30/9, p = 0.001 | 8/42 |
| rrf | 26/62 (42%, 30-54) | 51 | 32/2, p < 0.001 | 11/42 |

Decision, by the rule written first: not adopted. The rule asked for the Wilson intervals to be apart, and
38 against 33 overlap, so `ask` is unchanged and the packet stays at 20. The paired comparison is strong on
both sets and the gain is 19 points, which an interval rule at n = 62 cannot see; a next pre-registration
would name the paired test as primary before running, on a fresh set drawn from real asks. The BM25 arms also
pull longer units up (top 10 about 10.5k tokens against the store's 6.8k), so a smaller packet is not a free
consequence of a better rank. The final gate for any change stays the ask eval on set 2.

Also added the same day: `groundworks store supervise` (adopt, start, restart, daily export) with
`store install` registering it at logon on Windows; the selftest kills the store it started and checks that
it comes back.

## Retrieval ladder r2 to r5 and the ask evals r8 to r11 (2026-10-26 to 27)

The ladder was re-run with the paired sign test as its primary and the pool widened to the union of every
project's read at depth 60 (r2): BM25 over the read put the gold first on 29 of 62 against the store's 16,
and was adopted into `ask` with the packet cut from 20 to 8 by a rule that counted a gold unit in the
packet. The ask eval on set 2 refused that (r8): agents asked more to find what the smaller packet left out,
lost three correct answers, and gave two confidently wrong answers on questions whose two disagreeing
sources must both be in view. A second cause came out of the next run and was fixed: recorded facts had
been ranked with the units and fell out of most packets. With facts first and the packet back at 20, the
BM25 order alone (r10) still cost more tokens than the store's order, not fewer: under it the top 20 by
count is 24k tokens against 14k, because whole-unit scoring favours long units with the question's words
scattered through them.

So the ladder measured orders at a fixed packet cost instead (r4, r5): with the packet filled by bytes up to
40 KB, today's median, the gold unit was in the packet on 53 of 62 questions under a fusion of the store's
order and stemmed BM25, against 42 under the store's order and 50 under BM25 alone; set 1 agreed, 35
against 26 of 42. That packet, facts first, is what `ask` now builds, and r11 measured it on set 2 against
r7 on the same 66 questions (one trap was dropped after its premise became true):

| | r7, store order, 20 candidates | r11, fused order, 40 KB packet |
|---|---|---|
| reworded correct | 42/46 | 41/46 |
| lessons in notes correct | 19/20 | 18/20 |
| confidently wrong | 0 | 1 |
| conflict questions | 9 correct, 3 partial | 9 correct, 3 partial |
| sessions that saw a recorded fact | 61/66 | 62/66 |
| median tokens per question | 110k / 105k | 80k / 80k |
| median turns | 6 | 5 |

Correctness within the noise floor at a quarter fewer tokens; 40 of the 66 questions cost less than before.
It ships. Two things the series settled: rank was never where correctness was lost on these sets (the
agent had the gold file in front of it on its first call on 42 of 42 questions from r1 on), and the cost of a
packet is set by its bytes, which an order that favours long units raises even as it improves the rank.
Dead ends, each with its numbers in the private run folders: the packet of 8, facts ranked with the units,
the BM25 order by count, a wider stop-listed query (better recall, worse rank), and the question's own
project first (the lessons in notes are asked under other projects). Set 2 has now been used five times and
decides nothing further in this lane; the next change needs a fresh set drawn from real asks.
